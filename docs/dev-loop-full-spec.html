01

Where every part runs

Three environments, cleanly split. The agent's brain is on Anthropic's cloud; all the plumbing and state is on GitHub's cloud; the only thing on your hardware is the one test no machine can do.

Anthropic cloud

the reasoning
  • Build agent — Claude Code cloud session, Auto Mode, in a managed sandbox
  • Review agent — the code-review model call from CI
  • Captain agent — drafts release notes
  • The Routine that turns an issue webhook into a session

GitHub cloud

the plumbing & state
  • Repo, branches, issues, PRs, releases — the system of record
  • Actions runners — CI, gatekeeper, release build (free on public repos)
  • Branch protection + required-status-check rules
  • The webhook that fires the Routine

Your Windows PC

the irreducible human step
  • The alpha soak — overlay running against the live RotMG client
  • The "Report bug" capture that seeds the next fix
  • Two clicks: label an issue, dispatch a release
The two cloud boundaries that matter

Only two things cross from GitHub → Anthropic: the issue/PR text (the brief) and the repo contents (cloned into the sandbox). Only two things cross back Anthropic → GitHub: git pushes (the agent's branch) and PR comments/verdicts. Everything else — merges, tags, builds, releases — happens entirely inside GitHub. That's what keeps the Anthropic dependency to a single swappable box.

What enforces each rule

Every guarantee in this system is pinned to a concrete file or setting — nothing relies on anyone remembering to do the right thing. The A/G/W tag shows where it lives (Anthropic / GitHub / your machine).

File / settingLocEnforces
CLAUDE.md (repo root)GConventions the agents obey verbatim: build recipe, wire-format contract, Conventional Commits, and the never-release-without-ask rule. Read at the start of every session.
.github/ISSUE_TEMPLATE/feature.ymlGForces the fields that replace live questions: scope, acceptance criteria, out-of-scope, files/area.
.github/ISSUE_TEMPLATE/bug_report.ymlGForces build/version, steps·expected·actual, and the repro-capture attachment.
.github/workflows/ci.ymlGThe ground-truth gate: npm run typecheck + lint + gradle bridgeJar + JUnit DPS test. Emits the ci status check.
.github/workflows/review.ymlG → ARuns the code-review agent on pull_request; posts inline comments + the review verdict check. Model call happens on Anthropic.
.github/workflows/gatekeeper.ymlGMerges to staging only when ci and review are both green; re-triggers the builder on change-requests, capped.
.github/workflows/release.ymlGworkflow_dispatch only. Bumps overlay/package.json, tags, builds jar + --win --x64, publishes prerelease. Your ship button — human-triggered by design.
Routine config (issue webhook → session)AFires the build agent on issues: labeled. Auto Mode + tool allowlist define what it may do unattended.

The one you must add first

Two items above are prerequisites, not niceties: commit the Gradle wrapper (else CI can't build the jar) and set branch protection with 0 required approvals + required checks (else the gatekeeper either can't merge, or merges unreviewed). Everything else builds on those two.

04

Which model does what

Opus 4.8 for the reasoning-heavy work (build + review); Haiku only for the trivial drafting step. Effort is tuned per role — higher where correctness matters, lower where speed does.

RoleModelEffortWhy
Build agentclaude-opus-4-8high → xhighThe hard part — reads the codebase, implements, self-verifies. Opus 4.8 is the strongest coding/agentic model; xhigh for gnarly features, high as default.
Review agentclaude-opus-4-8highMust catch what the builder got wrong — needs to be as capable as the builder, and independent (adversarial prompt vs. acceptance criteria). A weaker reviewer rubber-stamps.
Auto Mode classifierSonnet (managed)—Anthropic runs this under the hood to approve each action unattended — you don't configure it.
Release-notes captainclaude-haiku-4-5lowSummarizing Conventional Commits between two tags is trivial — the one place a cheaper model is worth it. Optional; Opus works too.

List pricing per 1M tokens (in / out): Opus 4.8 $5 / $25 · Haiku 4.5 $1 / $5. Prompt caching drops repeated context to ~0.1× input — which is why an agentic loop that re-sends its context every turn is far cheaper than the raw token count suggests. These rates drive the estimate in §07.

05

Full run — a feature

Concrete example: "Add a Loot Tracker panel" — a new overlay panel that lists recent drops. Lives in overlay/src/renderer/, so it runs cleanly in parallel with anything on the Java side.

1
YouFile the feature issue

Use the feature form. Acceptance criteria: "panel registers via registry.ts; shows last 10 drops from the packet stream; sm/md/lg sizes; hidden when no drops." Apply agent:build. ~2 minutes of your time; nothing else until the PR.

2
AgentRoutine spins up a cloud session

Webhook → Auto-Mode session on Anthropic cloud, repo cloned, branch feature/loot-panel off staging. Opus 4.8, xhigh (new UI surface).

3
AgentBuilds and opens the PR

Adds the panel component + one registry.ts entry, wires it to DpsTracker's drop feed, runs typecheck/lint locally, and opens the PR — with an Assumptions block: "assumed 'drops' = ServerPlayerShoot loot events; assumed lg = 6 rows."

4
CIci.yml runs the ground-truth gate

Typecheck + lint + gradle bridgeJar (compiles clean since nothing Java changed) + the DPS test. Green.

5
Agentreview.yml scores the diff

Independent Opus review vs. the acceptance criteria. Catches that sizes were hard-coded, not preset via the panel system → requests changes with an inline comment.

6
AgentFix loop (round 1 of ≤3)

The change-request re-triggers the builder; it switches to the sm/md/lg preset dims, pushes. CI + review re-run → both green.

7
CIgatekeeper.yml merges to staging

ci ✓ and review ✓ → auto-merge, no human. The panel is now on staging.

8
YouDispatch the alpha, then soak

When enough is queued you run release.yml (alpha). CI publishes; the updater delivers it; you open the overlay on the live game and confirm the panel works. Done — or file a follow-up if a drop type is missing.

06

Full run — a bug

Concrete example: "DPS carries over across map changes" — you finished a dungeon, entered a new one, and the meter didn't reset. The bug lives in the Java bridge.dps engine (or DpsTracker.ts). The difference from a feature is the repro artifact.

1
YouHit "Report bug" in the overlay

The button bundles version + logs + a capture of the recent packet buffer (the JSON stream around the map change) and pre-fills a bug issue. You add the expected behavior: "DPS should zero on MapInfoPacket." Apply agent:fix.

2
AgentSession starts with the capture mounted

Branch fix/dps-map-reset off staging. The capture is the key: it lets the agent reproduce a live-game bug with no game. Opus 4.8, high.

3
AgentWrites a failing test from the capture first

Replays the captured stream through FakePacketSource → a JUnit test asserting DPS resets on MapInfoPacket. The test fails — the bug is now reproduced as ground truth.

4
AgentFixes until the test passes, opens the PR

Adds the reset-on-instance-change branch; the new test goes green. PR body links Fixes #N and includes the regression test.

5
CIci.yml runs — now with the new test

The regression test is part of the suite from now on, so this bug can never silently return. Green.

6
Agentreview.yml approves

Diff matches the acceptance behavior and is covered by a test → verdict pass, no loop needed.

7
CIgatekeeper merges to staging

Auto-merge on both-green. Fixes #N closes the issue.

8
YouTargeted re-test in the next alpha

The alpha notes list "fixed #N", so you re-verify only the map-reset path, not the whole app. It holds → promote to bridge when the train is green.

Why the bug run converges and a naive one doesn't

Steps 1 and 3 are the whole game: a replayable capture turns a "can't-reproduce-without-the-game" report into a failing test, and the fix ships with that test. That's what makes the manual-testing strategy a converging loop instead of whack-a-mole.

07

What it costs to run

Two cost centers: GitHub and Anthropic. The first is basically free; the second is the real number, and it's smaller than raw token counts suggest because agentic loops are cache-dominated.

GitHub — ~$0

Actions is free on public repositories for standard Linux and Windows runners. Since this repo is public, CI, the gatekeeper, and the release build cost nothing in Actions minutes. Storage for release assets is negligible. Call it $0/month.

Anthropic — the real cost

Per-task, metered at API list price (Opus 4.8 $5/$25). The numbers below assume prompt caching (~0.1× on repeated context, which the cloud session does automatically), a multi-turn build, plus review and any fix-loop rounds. Ranges, not promises — effort setting and task size move them a lot.

Unit of workBuildReview ×roundsNotes / total
Merged bugfix (scoped)~$1–3~$0.3–1Usually 1 review round. ≈ $2–5 each.
Merged feature (moderate)~$3–6~$0.6–2Often 1–2 rounds. ≈ $4–10 each.
Release notesHaiku—~$0.02. Rounding error.

Monthly, at a moderate solo cadence — say ~15 features + ~25 bugfixes: roughly 15 × $7 + 25 × $3.5 ≈ $190/month metered. A realistic band across light-to-heavy months is ~$100–400/month. GitHub adds $0.

You have Max — so the real bill is ~$0 on top of it

Both agents can run on your Claude Max subscription, not per-token API. The build agent is a Claude Code cloud session — that's natively Max (Max is exactly what unlocks Claude Code on the web / Routines). The CI review agent normally wants an ANTHROPIC_API_KEY, but claude-code-action also accepts a claude_code_oauth_token — generate one from your Max login with claude setup-token, store it as a repo secret, and the review agent draws from Max too. Net: no metered API at all — the table above is the "if you ever meter it through the API instead" figure.

The catch with Max — it's a usage ceiling, not unlimited

Max has rolling usage limits (a ~5-hour window plus weekly caps; the 20× (~$200) tier has far more headroom than 5× for parallel agents). Two things to know: heavy parallel agent runs can hit the cap, at which point sessions queue/pause until the window resets rather than failing; and pointing CI at the same Max account means your automation and your interactive Claude Code usage share one pool — a busy CI day can eat into your personal limit. If that bites, the escape hatch is putting just the CI review agent on a metered ANTHROPIC_API_KEY (the ~$0.3–2/PR figure above) so the build agent keeps the Max pool to itself.

  • Biggest lever: effort. Dropping the build agent from xhigh to high, or high to medium on routine bugs, cuts token spend materially — sweep it per task type.
  • Second lever: the fix-loop cap. Each extra round is another build + review. The ~3-round cap is a cost ceiling as much as a sanity one.
  • Not a lever: GitHub. Staying on a public repo keeps CI free — a private repo would start metering Actions minutes (Windows runners bill at 2×).

That's the whole machine. A labeled issue crosses to Anthropic as a brief, comes back as a branch, gets gated by ground-truth CI and an independent review inside GitHub, merges itself, and waits for you to press ship — with the only genuinely human steps being the issue you write, the alpha you test, and the two buttons you press. Every rule is pinned to a file in §03; the model behind each step is in §04; and at a solo cadence it runs for roughly a flat Max subscription plus $0 of GitHub.
