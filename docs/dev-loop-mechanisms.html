01

Issue + label kickoff

Drives
A maintainer applies agent:build/agent:fix. implement.yml runs on: issues: [labeled], gated by if: label.name == 'agent:build' || 'agent:fix'. Opening an issue alone does nothing.
Enforces
Label application is maintainer-only — it needs write/triage permission, so a stranger's issue can't start an agent. This is the loop's security boundary. Secondly, implement.yml no-ops if ROUTINE_FIRE_URL/ROUTINE_FIRE_TOKEN are unset.
Status
Built — verified on issue #10. Untrusted issue fields go through env vars, never interpolated into the shell.
Watch-out

A trailing newline in either secret silently 400s /fire with a misleading "could not parse request body as JSON". Set them with printf %s, never echo.

05

Independent review

Drives
review.yml runs on: pull_request: [opened, synchronize, reopened]. It invokes claude-code-action@v1 (Opus 4.8, CLAUDE_CODE_OAUTH_TOKEN), reads the diff, posts a review via POST .../pulls/{n}/reviews.
Enforces
The action's workflow-validation guard: it runs only if review.yml is byte-identical to the copy on the default branch. A PR can't rewrite the reviewer to rubber-stamp itself.
Status
Built — verified live on PR #22 (review-verdict = success). Both former gaps are closed (below).

Both problems now closed:

  • Machine-readable verdict — done. The prompt chooses REQUEST_CHANGES (any high/critical) or APPROVE, and publishes a review-verdict commit status. Downstream can gate on it; the fix loop has its "changes requested" signal.
  • No longer green-on-skip. The verdict is a separate review-verdict status, not the job's exit code — a validation-skip posts no status, so a required check fails closed instead of reading "approved".
Built in PR #21 — the review verdict (linchpin for §6 & §7)

Merged to staging + promoted to bridge in lockstep; verified by the review-verdict = success status on PR #22. How it works:

Decision rule (prompt): any high/critical finding → event: REQUEST_CHANGES; else event: COMMENT + status success (low/medium still listed, non-blocking). Not APPROVE — the Actions bot can't submit APPROVE reviews (the call fails and drops the summary; found live on #22/#19, fixed in #23). We gate on the status, not an approval.

Explicit status check (the gate): final step posts a commit status on the PR head SHA —

gh api -X POST repos/{repo}/statuses/{sha} \
  -f state=success|failure -f context=review-verdict

Fail-closed by construction: if the review skips or errors, no review-verdict status is posted, so a branch-protection rule requiring it leaves the PR blocked — the correct inverse of today's "green on skip". Then add review-verdict to required checks.

06

Fix loop — review requests changes → re-fire the builder (capped)

Unbuilt   The largest gap and the one most easily hand-waved, so it's specified in full. Nothing today triggers on review events. Depends on §5's verdict and §3's existing-branch mode.

6.1 · Normal (converging) path — exactly what happens

Trigger (Option B — workflow_run, chosen deliberately). A new fixloop.yml fires when the review workflow completes, then reads the verdict:

on:
  workflow_run:
    workflows: [review]
    types: [completed]

It pulls the PR's head branch + SHA from the workflow_run payload, ignores anything whose head isn't claude/*, reads the review-verdict status on that SHA, and acts only if it is failure; a success verdict is a no-op (the gatekeeper handles it).

Why workflow_run, not pull_request_review

The obvious trigger is the reviewer's REQUEST_CHANGES. But the reviewer posts that with the built-in GITHUB_TOKEN, and GitHub's recursion guard suppresses workflow triggers for events caused by GITHUB_TOKEN — so a pull_request_review trigger would silently never fire. workflow_run is GitHub's "chain off another workflow" event and fires regardless of token. Net: no non-default token is needed anywhere in the loop (§6.4).

Round counting (stateless — no fragile label state). rounds = count of non-dismissed CHANGES_REQUESTED reviews via GET .../pulls/{n}/reviews. The firing review is included, so rounds is 1 on the first change-request, 2 on the second… A loop:<n> label is set purely for human visibility.

Cap. MAX_FIX_ROUNDS = 3. If rounds ≤ 3 → re-fire (automated attempt #rounds). If rounds ≥ 4 → escalate (§6.2).

Re-fire — exact behavior. The job curls the same /fire endpoint with a FIX-MODE work item: "FIX MODE. PR #n, head claude/slug, base staging. Check out that branch, read the full PR conversation (review comments AND any maintainer comments) for guidance, address every unresolved comment below, and PUSH to the same branch — do NOT open a new PR. If a comment is wrong, reply to it instead of changing code." plus the verbatim review comments. The agent's push emits synchronize → CI and review re-run automatically → a fresh verdict.

Convergence. As soon as a round returns a passing verdict (review-verdict = success), §7 merges. So: request-changes → re-fire → push → re-review → … → pass → auto-merge, bounded at 3 automated attempts.

6.2 · Escalation — exactly how it stops and how you're flagged

When rounds ≥ 4, fixloop.yml does not re-fire. In one job, using the built-in GITHUB_TOKEN (with issues: write + pull-requests: write — these actions don't cascade, so no special token):

1
Stops the loop by inaction

It doesn't re-fire and doesn't push → no synchronize → nothing re-runs. The PR sits at its last CHANGES_REQUESTED → review-verdict = failure → not mergeable. There is no kill switch because there is nothing left running to kill.

2
Labels & freezes it

Adds agent:needs-human, removes loop:*, and runs gh pr merge {n} --disable-auto so it can't merge behind your back while you look.

3
Flags you — three native notifications

Posts a PR comment @-mentioning MAINTAINER_HANDLE (with the latest reviewer summary, the still-unresolved findings, and links to all 3 attempt reviews as an audit trail), and assigns the PR to you. The mention and the assignment each generate a GitHub notification → email + web + mobile. That's how you learn it's stuck without watching.

4
Exits 0

Escalation is a normal outcome, not a CI failure.

6.3 · Your input & resume — exactly what you do and what happens next

(a) Steer the agent

You apply the agent:retry label — optionally after dropping a comment with your steer. A small resume.yml runs on: pull_request: [labeled] with if: label.name == 'agent:retry' and:

• no auth filter needed — applying a label needs write permission, so GitHub already guarantees a maintainer (same gate as kickoff §1);
• resets the budget by dismissing the outstanding CHANGES_REQUESTED reviews (PUT .../reviews/{id}/dismissals) — since §6.1 counts only non-dismissed ones, rounds cleanly resets to 0;
• removes agent:retry + agent:needs-human, clears the assignee;
• re-fires FIX MODE — the prompt reads the PR thread, so any comment you left is picked up as guidance (nothing parsed from the label). Then it's the normal §6.1 loop again.

(b) Take over the code

You push commits to the claude/* branch (or edit in the UI). Your push fires synchronize → CI + review re-run on your commit.

If the new review APPROVEs, §7 merges it. A step in review.yml removes agent:needs-human whenever it posts a success verdict, so the "stuck" state clears itself once the PR is healthy.

(Your pushes re-run review because they're not made with the default GITHUB_TOKEN — see tokens, below.)

Resolution — both paths

Terminal state is identical to any PR: green CI + review-verdict = success → gatekeeper auto-merges to staging → Closes #N closes the issue → all loop:*/agent:* working labels removed on merge. No residue once resolved.

6.4 · What must be built for §6

  • fixloop.yml (on: workflow_run of review → read review-verdict → round count, re-fire, or escalate) — new. Runs on GITHUB_TOKEN.
  • resume.yml (on: pull_request labeled agent:retry → dismiss reviews → re-fire) — new.
  • A repo label agent:retry (maintainer-applied resume trigger) — new.
  • FIX-MODE branch in the routine prompt + FIX-MODE work-item construction — edit + new.
  • Repo variable MAINTAINER_HANDLE (escalation @-mention/assignee) — new.
  • Conflict → rebase FIX MODE — the branch in §6.5.
  • §5 verdict — hard dependency.
  • No GATEKEEPER_TOKEN / PAT — the workflow_run trigger sidesteps the recursion guard, and re-fires go through the routine (app/claude pushes, which already re-trigger CI/review). The loop runs on GITHUB_TOKEN + the existing ROUTINE_FIRE_TOKEN.

6.5 · Merge conflicts — nothing force-merges; it stalls, then rebases

A claude/* PR that conflicts with staging is mergeable: false / mergeStateStatus: DIRTY. GitHub's native auto-merge refuses a conflicted PR and disables itself, so a conflict never produces a bad merge — the PR just stalls. Handling:

  • When the gatekeeper (§7) finds an otherwise-green PR DIRTY, it does not merge — it re-fires the builder in FIX MODE with a rebase instruction: "merge origin/staging into claude/slug, resolve the conflicts, push — don't open a new PR." (reuses the §6.1 path).
  • The push → synchronize → CI + review re-run on the resolved tree → a fresh verdict, exactly like a normal fix round.
  • It counts against the same MAX_FIX_ROUNDS cap and escalates via §6.2 if the agent can't resolve it in budget — a genuinely hard conflict lands on your desk instead of looping.

Optional hardening: branch protection's "require branches up to date" (strict, currently off) surfaces staleness earlier by forcing a rebase before every merge — but it only surfaces conflicts, it doesn't resolve them.

07

Gatekeeper auto-merge

Drives
On CI + review completing for a claude/* PR into staging, gatekeeper.yml arms native auto-merge with no human.
Enforces
GitHub won't let a bot's approval satisfy protection, so protection requires status checks and the gatekeeper flips on native auto-merge once they pass.
Status
Built & verified — PR #19 (claude/dps-formatter → staging) auto-merged with zero human action: gatekeeper skipped non-agent branches, armed auto-merge on #19, native auto-merge merged once all 4 required checks went green.
How it works
  • Trigger: on: workflow_run completion of ci + review. Guard: same-repo, head claude/*, base staging.
  • Gate: merge only if both ci contexts = success and review-verdict = success and no agent:needs-human label.
  • Action: gh pr merge {n} --squash --auto with the built-in GITHUB_TOKEN — --auto hands off to native auto-merge. (It can merge here: 0 required approvals, no push restrictions, and the staging merge doesn't cascade, so the recursion guard is a non-issue.)
  • On verdict = failure: nothing; §6 owns that path.
  • On conflict (DIRTY): don't merge — re-fire the rebase FIX MODE (§6.5).
  • Prerequisites: enable the repo's "Allow auto-merge" setting (a toggle, not a token). No GATEKEEPER_TOKEN. A non-default token is only needed if you later add automation that must react to the staging merge — none today.

Manual overrides & the escape hatch

You're the owner, and enforce_admins is off on both branches (verified), so you bypass every gate — required checks, a failing review-verdict, an agent:needs-human freeze, all of it. Two hatches:

  • Force-merge a blocked PR (clean history): gh pr merge <n> --admin --squash. UI equivalent: the "Merge without waiting for requirements to be met" button, visible to you because admin-enforcement is off.
  • Land a commit directly, skipping PR + CI + review: git push origin <branch>:staging — works because you're an admin and restrictions: none. The deliberate "I've decided, ship it" hatch; nothing validated it.
Constraint & tradeoff

Force-pushes are blocked for everyone (allow_force_pushes: false) — normal pushes only. And these overrides exist only while enforce_admins is off: turn it on to stop anyone bypassing the loop and you lose the one-command hatch (you'd toggle protection off, act, toggle back). Recommendation: keep enforce_admins off — the loop's guarantees are for the agents; you overriding is a conscious human decision, not a hole an agent can exploit (agents can't apply labels or push to protected branches).

Merging outside / fork PRs

Anyone can open a PR (public repo), but a fork PR can't earn an automated review-verdict: a pull_request from a fork gets no secrets, so claude-code-action has no token and the reviewer can't run. The required check stays absent → the fork PR is fail-closed unmergeable through the normal path (a safety property, not a dead end). To land a good outside contribution, in increasing cleanliness:

  • Admin-merge — gh pr merge <n> --admin --squash. Bypasses all requirements (incl. CI) — review it yourself first. For tiny, self-evident PRs.
  • Manually stamp the verdict after you review: gh api -X POST repos/<repo>/statuses/<sha> -f state=success -f context=review-verdict. Merges through the normal button, and unlike --admin, CI still had to be green — you only substitute for the one check a fork can't produce.
  • Adopt as an internal branch (preferred). Pull their commits onto a same-repo branch, where secrets are available so the real reviewer runs: 
    gh pr checkout <n>
git push origin HEAD:contrib/<feature>
gh pr create --base staging --head contrib/<feature> --body "Supersedes #<n>, thanks @<author>"
    Git preserves the author's credit; the internal PR gets a genuine review-verdict and merges normally. Close the fork PR pointing at it. The only path that actually runs the review agent on their code — use it for anything non-trivial.

No GATEKEEPER_TOKEN (why the plan dropped it)

GitHub's recursion guard means GITHUB_TOKEN-caused events don't trigger further workflows. The only place that bit this design was the fix-loop trigger — so we chose the workflow_run trigger (§6.1), which fires regardless of token. Nothing in §6/§7 then needs elevated credentials: the gatekeeper merges on GITHUB_TOKEN (0 approvals, no push restrictions, staging merge doesn't cascade). A non-default token only becomes necessary if you later add automation that must react to an automation-made merge/push — none today.

Workflow-parity guard — keeps review from silently breaking

Built & verified   §5's guard keys off the default branch, so the instant a workflow change lands on bridge without staging being synced, every staging-based agent PR skips review — silently, with a green check (the exact failure fixed 2026-07-10).

How it works

A workflow parity job in ci.yml on every PR into staging/bridge. PRs into the default branch pass trivially (review.yml changes are legit there); anywhere else it fails if the merge result's review.yml differs from the default's:

git fetch --no-tags origin "+refs/heads/$DEFAULT:refs/remotes/origin/$DEFAULT"
git diff --quiet "refs/remotes/origin/$DEFAULT" -- .github/workflows/review.yml \
  || { echo "::error::review.yml differs — reviews will skip"; exit 1; }

Required on both branches, so the silent skip is now a loud, blocking failure. (The explicit refspec dodges a checkout@v4 false-positive — a review finding on PR #25.) Verified on the trivial path and a real → staging sync PR.
